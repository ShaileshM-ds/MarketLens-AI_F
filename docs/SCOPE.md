# MarketLens AI: Project Description

## 1. Purpose

MarketLens AI is an explainable marketplace intelligence platform. It helps shoppers and analysts compare offers, understand discounts, examine historical marketplace changes and make informed purchase decisions. Every conclusion is shown with its evidence and explanation. It is a decision aid, never a savings guarantee.

The app must help users answer:

- Is the advertised discount meaningful compared with previously observed prices?
- Is this product cheap, expensive or typical for its history?
- Which store or seller offers the most suitable comparable deal?
- What did the price, seller, availability and promotions look like on an earlier date?
- Is there enough evidence to buy now or wait?

## 2. Users and permissions

- Consumer: explores products, reads evidence and reviews, saves products, sets targets, receives alerts.
- Analyst: investigates movements, seller patterns, audit findings and model evaluation.
- Administrator: imports datasets, manages jobs, inspects rejected records, controls schedules and configuration.
  Watchlists and notifications belong to their owner. Administrative actions require the administrator role.

## 3. Data modes and provenance

- Demo: reproducible synthetic scenarios generated by the app, needing no paid service.
- Imported: uploaded datasets, with source and timestamp limits preserved.
- Live: newly collected observations through a configured provider (disabled until credentials and limits are set).
  The three modes use separate databases and are never mixed. A persistent badge shows the active mode, and charts, exports and notifications keep that label. An uploaded synthetic file never becomes real evidence.
  Every important record carries source, ingestion run, synthetic flag, observation time (if known), ingestion time, timestamp quality, raw source reference and schema version. Results are labelled as observed, calculated, estimated, forecast or simulated. Unknown information stays unknown.

## 4. Data model and money rules

- Launch categories: men's clothing, women's clothing, cameras, smart home, wearables, mobile phones, home appliances, computer accessories. More can be added later. Category attributes (size, storage, capacity) are filled only when supplied, never guessed.
- A product, a seller's offer and a timed observation are separate records. Products are never identified by title alone, and different variants, sizes, bundles or conditions are never merged. Historical observations are immutable.
- Money: store integer minor units (Rs 1,380 = 138000). Display only through one shared formatting function used by chart axes, tooltips, tables, filters and inputs. User price inputs are in rupees. Handle zero-decimal currencies such as JPY.
- Unknown shipping is never free; show "Total incomplete". Conditional coupons never reduce every user's displayed price.
- First dataset: a men's clothing snapshot (500 products, 3 stores each: Amazon, Flipkart, Myntra; 1,500 listings; all synthetic; one observation day). product_id links the same product across stores. "rating" is one review's rating; "product_rating" is shown per store. The file has no brand column, so brand stays blank. History-based features stay unavailable on this file and show the reason.

## 5. Features

Import (CSV, JSON, JSONL): choose file, profile, map fields, preview, validation warnings, confirm, results summary (accepted, duplicate, rejected, warnings). Keep originals, quarantine bad rows with plain reasons, never duplicate on reimport. Flag contradictions (for example Out of Stock with stock above zero) instead of fixing them. A later file of repeated observations for the same listings must append as new immutable observations.

Product explorer: search; category, brand, marketplace, currency, price, discount and coverage filters; sorting; pagination that resets on any filter change; grid and table views; compare tray (max 4).

Product page: breadcrumb, image, title, rating and review count, price with percent-off and original price, Buying advice card, store rows (item price, shipping, known total, Visit store), price-history chart with 7/30/90/180-day presets, and three tabs: Timeline, Evidence, Forecast. Features that need history explain why they are unavailable.

Analytics (each takes an explicit cutoff date):

- Real Price Detector: historical savings % = 100 x (baseline - current) / baseline. Baseline = median of daily comparable prices over the window, current observation excluded; negative results stay visible.
- Genuine Discount Score 0-100: 60% savings, 25% price percentile, 15% agreement with advertised discount. Missing components are disclosed; under 14 distinct observed days the score is "unavailable".
- Time Machine: date picker, scrubber, play/pause, previous/next, side-by-side comparison, changed fields highlighted; shows requested time, actual observation time and age. It reconstructs observed state, not archived web pages.
- Seller synchronization: needs repeated seller-level offers; results are patterns worth investigating, never proof of collusion.
- Future Price Memory: completed 1/3/7/14-day outcomes after similar past events, no overlapping episodes, frequencies not presented as probabilities.
- Forecasting: 7/14/30-day horizons where history suffices; chronological backtests against baselines; error metrics and measured interval coverage; fall back to a baseline if the model does not improve.
- Buying advice: Buy now, Consider waiting or Insufficient evidence, with reasons and disagreeing signals; sparse or stale data lowers confidence or abstains.
- Audit rules for dark patterns; each finding has rule version, severity, confidence, supporting observations and benign explanations; rules lacking required fields are disabled.

Comparison: up to 4 products, with warnings when variants, conditions or currencies are not comparable.

Watchlists and alerts: target price, notes, horizon, alert rules (below target, new low, meaningful discount, advice change, seller switch, restock, audit finding, synchronization anomaly), cooldowns, de-duplication, re-arm, read/unread, pause and delete. Delivery is in-app. Email is a local outbox stating nothing was sent. A signed-out Track price tap resumes after sign-in; adding an existing product merges settings.

Analyst dashboard and Data administration: summaries and tables (never raw JSON), ingestion runs, rejected records, job status, provider status without secrets, and a reset button that affects only the Demo database.

Demo data generator: you (the agent) write the generator and create all demo data. It is deterministic (fixed seed), and writes only to the Demo database. It creates:

- 30-50 fictional products across several categories, each with fictional brand names and the variant attributes that fit its category (for example size for clothing, storage for phones). Mark every value synthetic.
- 180+ days of daily price observations per product, with consistent seller IDs, several sellers on some products, and several observations per day from several sellers for a few products.
- 3-15 synthetic customer reviews per product, each with its own review rating, review text, and a "Synthetic sample review" label. Review text must be plain, varied and clearly fictional. Include some products with no reviews so the empty state can be checked.
- Scenarios for: genuine discounts, inflated reference prices, repeated urgency messages, shipping increases offsetting price drops, seller switches, broad market-wide movement, mixed event outcomes, stable prices, sparse or missing days, and insufficient history.
  Planted scenarios are written to a SEPARATE answer-key file that analytics code never reads. Export the generated data as CSV files in data/demo-export/ so a person can inspect it. Demo data is never mixed with Imported data.

## 6. Customer reviews

- Header shows product rating and review count.
- A reviews section lists each review with "Review rating N / 5" and a "Synthetic sample review" label when synthetic.
- Review rating and product rating are labelled separately; product rating is shown per store.
- Review text is plain text only. Reviewer names and dates appear only if the data has them.
- Empty state when no reviews.
- Not in scope: sentiment analysis, review summaries, fake-review detection, chatbot.

## 7. UI/UX

Follow the images in docs/design: lavender-to-white background, rounded white cards with soft shadows, solid blue active sidebar item, blue gradient primary buttons, green Buying advice card, purple price-history area chart, store rows with Visit store buttons.

- Answer first: verdict before detail; three product tabs.
- Plain language with a glossary; readable dates, not ISO strings.
- Text at least 12px; readable contrast; light and dark themes with theme-aware charts.
- URL routing: refresh and Back keep page, product, tab and filters.
- Every button acts or explains why it is unavailable.
- Responsive desktop and mobile; keyboard navigation; visible focus; reduced motion; chart summaries with data tables.
- Designed loading, empty, error, offline, stale-data and insufficient-history states.

## 8. Constraints

- Stack: React, TypeScript, Vite; TanStack Query; ECharts or equivalent; FastAPI and Pydantic; MongoDB; a separate Python worker with database-backed jobs; Docker Compose.
- Business logic is shared by API and worker, not duplicated in the UI.
- List endpoints must not read every observation of every product per request.
- Security: hashed passwords, secure sessions, ownership and role checks, request protection, rate limits, upload limits, restricted CORS, environment secrets, sanitized logs, safe rendering of imported text, URL allowlist. No reusable admin credentials in any public demo.
- Testing: unit, real-database integration, analytics, end-to-end and accessibility tests, including tests that price display is identical everywhere and pagination resets on filter change. Synthetic results are never presented as real-world effectiveness.
- No chatbot, LLM, vector database or extra database unless separately approved.
